博客维护确实适合交给 Agent 做一部分。

但我不建议一上来就让它从选题到发布全自动跑完。技术博客最值钱的是可信度，一旦连续发几篇没验证、像流水线摘要的文章，读者很快就会感觉不对。搜索流量也许还能骗一阵子，但长期没意义。

比较稳的做法是：Agent 做苦活，人做判断。

## Agent 适合做哪些事

这些工作重复、耗时，而且有检查清单就能约束质量：

- 搜索近期文档和工具变化
- 收集选题和关键词
- 生成文章大纲
- 检查链接是否失效
- 检查 frontmatter、标题、描述、标签
- 按模板生成初稿
- 对旧文提出更新建议
- 跑格式检查、lint 和构建

尤其是旧文维护，Agent 很适合。比如每个月扫一遍价格页、文档链接和版本号，把可能过期的地方列出来。人再决定要不要更新。

## 哪些事不该直接交出去

不建议让 Agent 直接决定这些事：

- 没有实际验证的命令能不能发
- 工具是否真的适合推荐
- 价格、额度和限制是否会误导读者
- 联盟链接或商业合作关系是否需要披露
- 涉及账号、服务器、客户数据的操作是否安全
- 一篇文章读起来是不是像真人写给读者的

这些不是模型“更聪明”就能完全解决的问题。它可以检查格式和事实来源，但很难替你承担信誉风险。

## 一个更稳的发布流程

我更倾向于这样的流程：

```txt
周一：收集选题和关键词
周二：跑实验，记录命令和截图
周三：写草稿
周四：检查技术细节、来源和链接
周五：改标题、description、首段和结构
周末：人看一遍，再发布
```

如果是每日资讯类文章，可以更快，但也要保留几个门槛：来源链接、人的判断、标题不像任务说明、构建通过。

## 本站目前怎么做

这个项目会把维护记录放在 `docs/` 目录里：

- `docs/PROJECT_LOG.md`：记录做过什么，方便下次接着做
- `docs/BLOG_OPS.md`：记录运营方向和发布原则
- `docs/SEO_STYLE_GUIDE.md`：记录标题、摘要、首段和真人化写作要求
- `docs/AUTOMATION_STATUS.md`：记录自动化任务当前跑到哪一步

Agent 可以负责草稿、检查和整理；真正发布前，要满足基本门槛：

1. title 和 description 像读者会看到的文章，不像内部日志
2. 首段说明为什么值得读
3. 每个事实或工具都有来源
4. 没有夸大结果、免费额度或能力
5. `format:check`、`lint`、`build` 都通过

## 我的结论

Agent 不是不能参与发布，而是不能没有刹车。

让它做选题、草稿、链接检查和旧文巡检，效率会高很多。让它完全决定内容质量、商业推荐和最终发布，就太冒险了。博客如果想长期做，宁愿慢一点，也别把可信度交给自动化流程赌运气。
