## 先把三个问题分开

很多 AI 自动化讨论容易把所有新词揉成一个“大模型应用架构”。这样写文章很热闹，做系统却容易混乱。

更实用的拆法是先问三个问题：

1. 回答依据从哪里来？这是 RAG 的问题。
2. 外部工具怎么接入？这是 MCP 这类协议要解决的问题。
3. 多步骤任务怎么被拆解、执行和收尾？这是 Agent 的问题。

这三个问题并不是替代关系，而是协作关系。RAG 不是 Agent，MCP 也不是 RAG 的升级版。把层次分清楚，系统才更容易测试、排错和约束风险。

## RAG 是资料层：让回答有依据

RAG 的核心价值不是“让模型更会聊天”，而是让回答能够回到资料。

在个人博客、内部知识库、代码仓库问答这类场景里，模型仅靠训练数据很容易过时，也容易补全出并不存在的细节。RAG 的做法通常是先检索相关片段，再把这些片段交给模型组织答案。这样至少可以把问题拆成两段：检索是否命中了正确资料，生成是否忠实使用了资料。

这也意味着 RAG 的边界很清楚：如果资料库没有收录，或者检索结果不相关，系统就应该承认依据不足，而不是假装知道。对技术博客自动化来说，这一点尤其重要。来源打不开、正文没读到，就不能把搜索结果包装成“原文总结”。

## MCP 是连接层：让工具可发现、可调用、可治理

当 AI 应用需要读取文件、操作浏览器、访问数据库、调用 GitHub 或连接内部系统时，问题就从“怎么找资料”变成了“怎么安全地接工具”。

MCP 的意义在于把外部能力包装成更统一的接口，让 AI 客户端可以理解有哪些工具、每个工具需要什么输入、会返回什么结果，以及调用时应该遵守哪些边界。它更像连接层或协议层，而不是某一种具体应用。

这层能力带来的好处是复用和治理。一个团队不必为每个 AI 客户端重复写临时集成；同一个工具也可以被不同工作流复用。与此同时，工具权限、失败状态和审计记录也应该在这一层被认真设计。

## Agent 是编排层：负责把任务跑完

Agent 关注的是流程。

如果用户只问“解释一下 MCP 是什么”，模型回答一次就够了。如果用户要求“搜索 CSDN 最近三天技术文章，选择一个选题，生成测试稿，更新状态文件，再运行格式、lint 和构建验证”，这就是多步骤任务。

在这种任务里，Agent 需要决定先搜索什么、候选结果是否可用、正文打不开时是否降级为选题线索、哪些文件允许修改、验证失败后如何处理。它不是一个单点能力，而是一套围绕目标、工具、状态和约束的执行方式。

因此，Agent 的质量不只看最后产物是否像样，还要看它有没有如实记录中间证据。比如这次 CSDN 正文被 WAF 拦截，正确行为就是明确写出来，而不是假装读到了正文。

## 小型内容自动化可以这样落地

如果把这套分层放回 Pace Notes 的内容自动化，我会按这个顺序落地：

1. 先固定资料入口和来源记录，确保每篇稿子知道自己基于什么。
2. 再把浏览器访问、文件写入、格式检查、构建验证做成清晰工具步骤。
3. 对发布、提交、推送这类外部可见动作保留人工确认。
4. 最后用 Agent 编排全流程，并把失败状态写进草稿或状态文件。

这样做不一定最炫，但更适合长期维护。内容质量不仅来自语言润色，也来自边界诚实：读到了什么、没读到什么、哪些判断是基于搜索结果、哪些判断是作者自己的整理。

## 这次测试得到的结论

本次浏览器测试说明：CSDN 搜索结果页可以作为选题入口，但正文页可能被 WAF 拦截。自动化流程应该允许这种失败状态存在，并把它变成可审计记录。

对技术写作来说，这个约束反而有价值。它提醒我们不要把“能搜索到标题”误认为“已经完成资料阅读”。一篇可信的自动化测试稿，首先要诚实说明来源状态，其次才是把主题改写成适合本站读者的结构化内容。
