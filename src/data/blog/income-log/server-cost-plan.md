个人技术博客最容易低估的不是写作成本，而是维护成本。

域名、构建、图片、搜索、评论、统计、后台、自动化任务，看起来每一项都不大，但只要组合得太复杂，后面排错、迁移和续费都会变成负担。早期更稳的做法，是先把基础设施做轻：页面能稳定访问，文章能正常归档，构建能复现，出错能回滚。

## 先选静态部署

如果只是技术博客，静态站点通常是最省心的起点。

AstroPaper 这类方案的好处是：文章在 Git 里，构建过程清楚，页面可以直接部署到 Cloudflare Pages。没有运行时服务器，就少了进程守护、数据库连接、系统升级和反向代理的一大堆问题。

这并不意味着永远不用后端。后台、搜索索引、评论、订阅都可以后面补。但第一版最好让核心内容不依赖复杂服务。

## 把文章当成主要资产

个人博客的核心不是主题动画，也不是后台面板，而是文章本身。

每篇文章至少要回答几个问题：

- 适合谁读？
- 解决什么具体问题？
- 需要哪些前置条件？
- 哪些步骤容易失败？
- 以后版本变化时应该复查哪里？

这些信息写清楚，文章才有长期价值。反过来，如果正文只是流水账，页面再漂亮也留不住读者。

## 功能要一层一层加

我会把博客功能分成三层：

1. **内容层**：Markdown、frontmatter、slug、标签、归档、RSS。
2. **运营层**：日期校验、草稿状态、自动化发布记录、文章质量检查。
3. **管理层**：后台登录、D1 索引、广告位配置、自动化运行审计。

第一层必须稳定；第二层用来减少人为失误；第三层只有在文章数量上来以后才真正有价值。

## 成本控制看哪些点

早期我更关注这些指标：

1. 构建是否稳定。
2. 文章日期是否不会被发布流程误改。
3. 草稿是否不会意外公开。
4. 搜索和归档是否能找到旧文。
5. 站点配置是否能用 Git 回滚。
6. 后台写操作是否有密码和审计。

这些指标看起来朴素，但决定了站点能不能长期维护。

## 我的判断

个人技术博客要先做轻，再做强。

先让文章、构建和部署可靠；再补后台、数据库和自动化；最后才考虑更复杂的交互能力。这个顺序慢一点，但每一步都能回滚，也更适合一个人长期维护。
